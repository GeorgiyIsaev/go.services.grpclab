# go.services.grpclab

Учебный стенд для изучения **gRPC** на Go. Цель проекта — на минимальном рабочем
примере пройти все четыре типа взаимодействия между клиентом и сервером, понять
устройство Protocol Buffers и научиться читать сгенерированный код не как магию,
а как понятную механику.

Проект не претендует на продакшн-качество: он намеренно упрощён, чтобы вся
существенная логика помещалась в один экран, а различия между паттернами были
видны «глазами».

## 📁 Структура проекта

```
go.services.grpclab/
├── go.mod                      # модуль проекта
├── proto/
│   └── random.proto            # единственный контракт: сервис + 4 метода
├── gen/
│   └── randompb/               # сгенерированный код (руками не редактируется)
│       ├── random.pb.go
│       └── random_grpc.pb.go
└── cmd/
    ├── ServerRandom/           # один сервер, реализует все 4 метода
    ├── ClientUnary/            # клиент Unary
    ├── ClientServerStream/     # клиент Server Streaming
    ├── ClientClientStream/     # клиент Client Streaming
    └── ClientBidiStream/       # клиент Bidirectional Streaming
```

### `proto/random.proto`

Единственный источник правды. Описывает сервис `Random` с четырьмя методами —
по одному на каждый тип RPC. Все сообщения (запросы и ответы) тоже объявлены
здесь. Изменение этого файла — единственный способ поменять контракт.

### `gen/randompb/`

Код, сгенерированный `protoc` из `random.proto`. Содержит:
- `random.pb.go` — Go-структуры сообщений и их сериализация;
- `random_grpc.pb.go` — интерфейсы `RandomClient` и `RandomServer`,
  функция `RegisterRandomServer`, а также вся «проводка» gRPC.

Руками не редактируется: при изменении `.proto` файлы перегенерируются.

### `cmd/ServerRandom`

Единственный серверный бинарник. Реализует все четыре метода сервиса `Random`.
Слушает `:50051`, включён reflection — сервер можно исследовать через `grpcurl`
или `grpcui` без дополнительных `.proto`-файлов.

### `cmd/ClientUnary`

Клиент **Unary RPC**: один запрос — один ответ. Дёргает `GetRandom`, печатает
полученное число и завершается.

### `cmd/ClientServerStream`

Клиент **Server Streaming RPC**: один запрос — поток ответов. Открывает
`StreamRandom`, читает в цикле, пока сервер не закроет поток. Корректно
реагирует на Ctrl+C (отмена через контекст).

### `cmd/ClientClientStream`

Клиент **Client Streaming RPC**: поток запросов — один ответ. Отправляет
`UploadNumbers` поток случайных чисел, затем получает от сервера агрегат:
количество, сумму, среднее, минимум, максимум.

### `cmd/ClientBidiStream`

Клиент **Bidirectional Streaming RPC**: поток запросов ↔ поток ответов.
Отправляет `CompareNumbers` числа в отдельной горутине, одновременно читает
ответы сервера. Сервер на каждое число отвечает своим случайным числом и
вердиктом «кто больше».

## 📚 Теория

### gRPC в одном абзаце

**gRPC** — это фреймворк для удалённого вызова процедур поверх HTTP/2. Клиент
вызывает метод как локальную функцию, а gRPC берёт на себя сериализацию,
передачу по сети и десериализацию. Контракт описывается в `.proto`-файле на
языке **Protocol Buffers**, из которого автоматически генерируется код для
клиента и сервера.

### Protocol Buffers (protobuf)

**Protobuf** — это:
1. **Язык описания контракта** (IDL). `.proto` файл описывает сервисы, методы
   и сообщения.
2. **Бинарный формат сериализации**. Компактнее и быстрее JSON.
3. **Кодогенератор**. Плагины генерируют код на нужном языке.

Ключевые правила `.proto`:

- `syntax = "proto3";` — всегда первая строка.
- `package` задаёт полное имя сервиса в сети (например, `random.Random`).
- `option go_package` указывает, куда класть Go-код и как называть пакет.
- Поля нумеруются: `int32 value = 1;`. **Номер поля нельзя менять после
  релиза** — иначе клиент и сервер перестанут понимать друг друга.
- Имена: сервисы и сообщения — `PascalCase`, поля — `snake_case`, методы —
  `PascalCase`.
- `<MethodName>Request` / `<MethodName>Response` — стандартная схема имён
  сообщений для метода.

### Четыре типа RPC

Тип вызова определяется двумя вопросами: сколько сообщений шлёт клиент (одно
или поток) и сколько шлёт сервер (одно или поток). **Инициатор вызова всегда
клиент** — сервер не может «сам» постучаться к клиенту.

| | Сервер отвечает **одним** | Сервер отвечает **потоком** |
|---|---|---|
| **Клиент шлёт одно** | Unary | Server Streaming |
| **Клиент шлёт поток** | Client Streaming | Bidirectional Streaming |

### Как это выглядит в `.proto`

```protobuf
// Unary: stream отсутствует с обеих сторон
rpc GetRandom(GetRandomRequest) returns (GetRandomResponse);

// Server Streaming: stream справа
rpc StreamRandom(StreamRandomRequest) returns (stream StreamRandomResponse);

// Client Streaming: stream слева
rpc UploadNumbers(stream UploadNumbersRequest) returns (UploadNumbersResponse);

// Bidirectional: stream с обеих сторон
rpc CompareNumbers(stream CompareNumbersRequest) returns (stream CompareNumbersResponse);
```

`stream` слева от `returns` — «эта сторона шлёт много сообщений».

### Как это выглядит в Go

Разница между паттернами видна прямо в сигнатурах клиента и сервера.

**Клиентская сторона:**

| Паттерн | Открытие вызова | Отправка | Чтение | Завершение |
|---|---|---|---|---|
| Unary | `client.M(ctx, req)` | — | ответ сразу | автоматически |
| Server Stream | `client.M(ctx, req)` | — | `Recv()` в цикле | `io.EOF` на `Recv` |
| Client Stream | `client.M(ctx)` | `Send()` в цикле | один ответ | `CloseAndRecv()` |
| Bidi | `client.M(ctx)` | `Send()` в горутине | `Recv()` в цикле | `CloseSend()` + `io.EOF` |

**Серверная сторона:**

| Паттерн | Сигнатура метода | Чтение | Отправка |
|---|---|---|---|
| Unary | `func(ctx, req) (resp, err)` | — | `return resp, nil` |
| Server Stream | `func(req, stream) error` | — | `stream.Send()` много раз |
| Client Stream | `func(stream) error` | `stream.Recv()` в цикле до `io.EOF` | `stream.SendAndClose(resp)` |
| Bidi | `func(stream) error` | `stream.Recv()` в цикле | `stream.Send()` в цикле |

### Ключевые понятия

**Инициатор — всегда клиент.**
Сервер физически не имеет соединения с клиентом, пока тот сам его не открыл.
Если нужно «чтобы сервер что-то присылал сам», это делается через Server
Streaming (клиент подписывается и держит вызов открытым) или через Unary с
задержкой (long polling). В чистом виде push-модели в gRPC нет.

**`io.EOF` — это не ошибка.**
В потоках `io.EOF`, полученный на `Recv()`, означает «отправитель закончил и
корректно закрыл свою сторону». Любая другая ошибка — сбой. Проверять через
`errors.Is(err, io.EOF)`.

**`CloseSend` vs `CloseAndRecv`.**
- `CloseSend()` — закрыть только отправку, продолжить читать (используется в Bidi).
- `CloseAndRecv()` — закрыть отправку **и** прочитать ровно одно ответное
  сообщение (используется в Client Streaming).

**Контекст — обязательный первый аргумент.**
Каждый вызов принимает `context.Context`. Через него приходят отмены и
дедлайны. `context.WithTimeout` защищает от бесконечного ожидания. `defer
cancel()` обязателен сразу после создания контекста.

**Отмена распространяется в обе стороны.**
Если клиент отменяет контекст (Ctrl+C, истёк дедлайн), сервер мгновенно видит
это через `stream.Context().Done()` и должен корректно завершиться. Это
касается всех четырёх паттернов.

**Геттеры у сгенерированных структур — методы.**
`resp.GetValue()` — вызов метода, а не обращение к полю. Геттеры безопасны к
`nil`-получателю, поэтому их использование — стандартный стиль protobuf-кода.

**Порты.**
Всего 65 536 портов (0–65535), потому что порт — 16-битное число.
Диапазоны: 0–1023 (системные), 1024–49151 (пользовательские),
49152–65535 (динамические). Порт `50051` из примеров gRPC — просто
нейтральное значение из «свободной зоны», не техническое требование.
Один порт на одном IP может слушать только один процесс: второму `bind`
вернёт `address already in use`.

**Клиенты не мешают друг другу.**
Сервер слушает один порт, но каждое входящее соединение — отдельный сокет,
а каждый вызов обслуживается в отдельной горутине. Переменные внутри метода
локальны для вызова, поэтому два клиента не портят данные друг другу.

### Генерация кода

```powershell
protoc `
  --go_out=. --go_opt=module=go.services.grpclab `
  --go-grpc_out=. --go-grpc_opt=module=go.services.grpclab `
  proto/random.proto
```

Плагины `protoc-gen-go` и `protoc-gen-go-grpc` должны быть в `PATH`. Сам
`protoc` устанавливается отдельно (например, `winget install protobuf`).

### Полезные инструменты

- **`grpcurl`** — «curl для gRPC». Позволяет дёргать методы из командной строки.
- **`grpcui`** — веб-интерфейс для ручного тестирования сервера.
- **reflection** — сервер отдаёт свою схему по запросу, что позволяет
  использовать `grpcurl`/`grpcui` без `.proto`-файла на клиенте.

## 🏁 Итог

После прохождения проекта должны остаться следующие ключевые понимания:

1. **`.proto` — единственный источник правды.** Меняете контракт — правите
   только `.proto`, всё остальное перегенерируется.
2. **Один `.proto` рождает код для двух сторон.** Клиент получает
   `RandomClient`, сервер — `RandomServer`, но оба импортируют один и тот же
   пакет `gen/randompb`.
3. **Инициатор вызова всегда клиент.** Ни в одном из четырёх паттернов
   сервер не начинает первым. «Push» — это всегда Server Streaming поверх
   открытого клиентом вызова.
4. **Разница между паттернами — это разница в сигнатурах.** Четыре паттерна
   отличаются только тем, где стоит `stream` в `.proto` и какие методы
   появляются у клиента и сервера. Никакой другой магии нет.
5. **Поток — это цикл `for { Recv() }`.** Внутри gRPC нет ничего
   «реактивного»: клиент и сервер просто читают и пишут в цикле, пока не
   получат `io.EOF` или не отменят контекст.
6. **Отмена — через контекст.** Это основной и обязательный механизм
   завершения работы с потоками. Работает симметрично в обе стороны.
7. **Клиенты изолированы друг от друга.** Один порт, много соединений,
   отдельная горутина на каждый вызов, локальные переменные внутри метода.
8. **Сгенерированный код — это не «лишний» код, а фундамент.** Каркас HTTP/2,
   сериализация, диспетчеризация методов — всё это делает `protoc`, а
   разработчик пишет только бизнес-логику.
