# ClientServerStream

Клиент **Server Streaming RPC** — второй по сложности из четырёх паттернов.

Клиент делает **один** запрос и получает **поток** ответов от сервера. Сервер
отправляет сообщения по мере готовности, клиент читает их в цикле, пока
сервер не закроет поток.

Это первый паттерн, в котором появляется **время**: ответ приходит не сразу
целиком, а растянут во времени. Именно поэтому здесь впервые возникает
необходимость в отмене через контекст — иначе клиент может «зависнуть»
навсегда, слушая бесконечный поток.

---

## 🎯 Что делает клиент

1. Открывает gRPC-соединение с `ServerRandom` на `localhost:50051`.
2. Делает **один** вызов `StreamRandom`, передавая параметры:
    - `interval_seconds = 2` — сервер шлёт числа раз в 2 секунды;
    - `count = 5` — всего 5 сообщений, потом сервер закроет поток.
3. Читает поток в цикле `for { Recv() }`.
4. На каждое сообщение печатает значение и время генерации.
5. Получив `io.EOF`, завершается.
6. Умеет корректно прерываться по Ctrl+C — контекст отменяется, поток
   закрывается, сервер узнаёт об этом.

## 📚 Теория: Server Streaming RPC

### Определение

**Server Streaming RPC** — паттерн, в котором клиент отправляет **одно**
сообщение, а сервер отвечает **потоком** сообщений. Клиент читает их по
одному, пока сервер не закроет свою сторону.

Это единственный паттерн, в котором сервер может отправлять данные **с
инициативой по времени** (раз в N секунд, по событию, по мере готовности),
а не одним куском. При этом **инициатор вызова всё равно клиент** — он
открывает вызов, а сервер пользуется этой открытой дверью, чтобы шлёпать
сообщения.

### Как выглядит в `.proto`

```protobuf
rpc StreamRandom(StreamRandomRequest) returns (stream StreamRandomResponse);
```

Ключевой признак: **`stream` стоит справа** от `returns`, перед типом ответа.
Это буквально читается как «сервер отвечает потоком `StreamRandomResponse`».

Слева `stream` нет — клиент шлёт один запрос.

### Как выглядит в Go

**Клиент:**
```go
stream, err := client.StreamRandom(ctx, req)
for {
    resp, err := stream.Recv()
    if errors.Is(err, io.EOF) { break }
    // ...обработка resp
}
```

**Сервер:**
```go
func (s *server) StreamRandom(req *pb.StreamRandomRequest, stream pb.Random_StreamRandomServer) error {
    for {
        // ...подготовка resp
        if err := stream.Send(resp); err != nil { return err }
    }
}
```

Разница с Unary видна сразу:
- У клиента вместо `resp, err := client.M(...)` теперь `stream, err := client.M(...)`, а сам ответ приходит через `stream.Recv()`.
- У сервера вместо `(ctx, req) → (resp, err)` теперь `(req, stream) → error`. Ответ уходит через `stream.Send()`, а не через `return`.

## 📝 Разбор кода

```go
package main

import (
	"context"
	"errors"
	"io"
	"log"
	"os"
	"os/signal"
	"syscall"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/credentials/insecure"

	pb "go.services.grpclab/gen/randompb"
)

func main() {
	conn, err := grpc.NewClient(
		"localhost:50051",
		grpc.WithTransportCredentials(insecure.NewCredentials()),
	)
	if err != nil {
		log.Fatalf("не удалось подключиться: %v", err)
	}
	defer conn.Close()

	client := pb.NewRandomClient(conn)

	// Контекст, отменяемый по Ctrl+C.
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	sigCh := make(chan os.Signal, 1)
	signal.Notify(sigCh, os.Interrupt, syscall.SIGTERM)
	go func() {
		<-sigCh
		log.Println("получен сигнал, закрываем поток...")
		cancel()
	}()

	req := &pb.StreamRandomRequest{
		IntervalSeconds: 2,
		Count:           5,
	}
	log.Printf("отправляем запрос: interval=%ds, count=%d", req.IntervalSeconds, req.Count)

	stream, err := client.StreamRandom(ctx, req)
	if err != nil {
		log.Fatalf("не удалось открыть поток: %v", err)
	}

	log.Println("ждём сообщения от сервера...")
	for {
		resp, err := stream.Recv()

		if errors.Is(err, io.EOF) {
			log.Println("сервер закрыл поток")
			return
		}
		if err != nil {
			if ctx.Err() != nil {
				log.Println("поток закрыт клиентом")
				return
			}
			log.Fatalf("ошибка приёма: %v", err)
		}

		log.Printf("получено: значение=%d, время=%s",
			resp.GetValue(),
			time.Unix(resp.GetTimestampUnix(), 0).Format(time.TimeOnly),
		)
	}
}
```

### Пошаговый разбор

**`context.WithCancel(...)` вместо `WithTimeout`.**

В Unary мы ставили дедлайн — короткий вызов, ответ приходит сразу.
В Server Streaming поток может жить долго, поэтому вместо жёсткого таймаута
мы хотим **управляемую отмену**: клиент сам решает, когда закончить.
`WithCancel` возвращает функцию `cancel`, которую мы вызовем при Ctrl+C.

**Перехват Ctrl+C через `signal.Notify`.**

`signal.Notify(sigCh, os.Interrupt, syscall.SIGTERM)` подписывает канал на
сигналы Ctrl+C (SIGINT) и SIGTERM. Отдельная горутина ждёт сигнал и вызывает
`cancel()`. Это не «выход из программы» — это корректная отмена контекста,
которая передаётся на сервер как RPC-статус `Canceled`.

**`client.StreamRandom(ctx, req)` возвращает `(stream, error)`.**

Не ответ, а **объект-стрим**. Ошибка на этом шаге — это ошибка соединения,
а не ошибка обработки. Успешное открытие потока означает только одно:
соединение установлено, сервер принял вызов, готов слать сообщения.

**`stream.Recv()` в цикле — сердце клиента.**

Каждый вызов `Recv()`:
- **блокируется**, пока не придёт следующее сообщение (или поток не
  завершится);
- возвращает `(*StreamRandomResponse, nil)` при успехе;
- возвращает `(nil, io.EOF)` при **нормальном** завершении потока;
- возвращает `(nil, err)` при сбое (сеть, отмена, ошибка на сервере).

**`errors.Is(err, io.EOF)` — проверка «нормального конца».**

`io.EOF` означает: сервер корректно завершил метод, поток закрыт с его
стороны, новых сообщений не будет. Это не ошибка, а сигнал «всё, приехали».
Проверяем **до** общего `err != nil`, потому что `io.EOF` тоже является
`error`, но обрабатывать его надо иначе.

Используйте `errors.Is`, а не `err == io.EOF`. gRPC может оборачивать ошибки,
и прямое сравнение не сработает.

**Проверка `ctx.Err() != nil` для отмены.**

Если `Recv()` вернул ошибку, и при этом `ctx.Err() != nil` — значит, вы
сами отменили контекст. Это не повод для `log.Fatalf`, просто тихо выходим.
Если `ctx.Err() == nil` — ошибка пришла извне, это настоящий сбой.

**`resp.GetTimestampUnix()` — со скобками.**

`GetTimestampUnix` — метод-геттер, как и `GetValue`. Возвращает `int64`
(секунды с эпохи Unix). Передаём в `time.Unix(sec, 0)`, получаем `time.Time`.

## 🧪 Что попробовать

**1. Бесконечный поток и Ctrl+C.**

Поставьте в клиенте `Count: 0` — сервер не остановится сам. Через несколько
секунд нажмите **Ctrl+C** в терминале клиента:

Клиент:
```
получен сигнал, закрываем поток...
поток закрыт клиентом
```

Сервер:
```
[ServerStream] клиент отключился
```

Это самый важный момент для понимания Server Streaming. **Сервер узнаёт об
отключении мгновенно**, через `stream.Context().Done()`. Он не ждёт
следующей попытки `Send`, не шлёт «в пустоту». Отмена контекста на клиенте —
это RPC-статус `Canceled`, который доходит до сервера через сеть.

**2. Убить сервер посреди потока.**

Запустите клиент с `Count: 0`, через пару секунд нажмите Ctrl+C в терминале
**сервера**. Клиент получит на `Recv()`:
```
ошибка приёма: rpc error: code = Unavailable desc = ...
```
`log.Fatalf` завершит клиент. Обратите внимание: это **не** `io.EOF`, а
настоящая ошибка. Поток порвался без корректного завершения — клиент не
переподключается сам.

**3. Два клиента одновременно.**

Запустите клиент в двух окнах. У каждого — **свой независимый поток**, со
своим расписанием. Сервер обслуживает их параллельно, в отдельных
горутинах. Один клиент нажмёт Ctrl+C — второй этого даже не заметит.

**4. Изменить интервал и количество.**

- `IntervalSeconds: 1, Count: 10` — быстрее и больше.
- `IntervalSeconds: 0` — сервер применит дефолт из своей логики (5 секунд).
- `Count: 0` — поток до отключения клиента.

**5. Проверить через `grpcurl`.**

`grpcurl` печатает поток как JSON-объекты в реальном времени, пока вы не
нажмёте Ctrl+C:
```powershell
grpcurl -plaintext -d "{\"interval_seconds\": 1, \"count\": 3}" localhost:50051 random.Random/StreamRandom
```

Ожидаемый вывод (с паузами в секунду между строками):
```json
{"value": 4, "timestampUnix": "1728135600"}
{"value": 2, "timestampUnix": "1728135601"}
{"value": 7, "timestampUnix": "1728135602"}
```

После третьего сообщения сервер закроет поток, `grpcurl` завершится сам.

## ⚠️ Типичные ошибки

**`cannot use resp.GetTimestampUnix (value of type func() int64) as int64`**

Забыли скобки у геттера. Правильно: `resp.GetTimestampUnix()`.

**`rpc error: code = Unavailable desc = connection error`**

Сервер лежит или слушает другой порт. Или (частая причина в учебном
проекте) на порту висит **старый** сервер, у которого нет метода
`StreamRandom`. Проверьте через `grpcurl describe random.Random`, что метод
на месте.

**Клиент «зависает» и ничего не делает**

Скорее всего, сервер не шлёт сообщения — например, интервал слишком большой
или сервер не запустил `ticker`. Посмотрите логи сервера: если там нет строк
`[ServerStream] отправлено #N`, проблема на стороне сервера.

**`log.Fatalf` при Ctrl+C**

Если клиент завершается с ошибкой вместо тихого выхода — забыта проверка
`ctx.Err() != nil` перед `log.Fatalf`. При отмене через контекст `Recv()`
возвращает ошибку `context canceled`, и это нормальное завершение, а не сбой.

**Ошибка `stream.Send` на сервере: `SendMsg called after CloseSend`**

Это серверная ошибка: `Send` вызван после того, как клиент отменил контекст.
В нашем серверном коде это предотвращено через `select` по
`stream.Context().Done()`.

## 🧠 Ключевые выводы

1. **Один вызов — много ответов.** Server Streaming расширяет Unary на
   случай, когда серверу нужно отправить данные по частям.
2. **`client.M(ctx, req)` возвращает стрим, а не ответ.** Ответ приходит
   через `stream.Recv()` в цикле.
3. **`io.EOF` на `Recv()` — это нормальное завершение потока**, а не ошибка.
4. **Сервер должен уважать отмену клиента.** Через `stream.Context().Done()`
   он узнаёт, что клиент отключился, и корректно завершается. Иначе будут
   утечки горутин и «слать в пустоту».
5. **Клиент должен уважать отмену контекста.** При Ctrl+C `Recv()` вернёт
   ошибку `context canceled` — это ожидаемое поведение, не сбой.
6. **Два клиента не мешают друг другу.** Каждый вызов — отдельная горутина
   на сервере и отдельный сетевой поток.
7. **Server Streaming — основа для «вещания».** Подписки, стриминг логов,
   метрики в реальном времени, поток показаний датчика — всё это сюда.

## 🔗 Сравнение с другими паттернами

| Что | Unary | **Server Stream** | Client Stream | Bidi |
|---|---|---|---|---|
| Клиент шлёт | 1 | **1** | поток | поток |
| Сервер шлёт | 1 | **поток** | 1 | поток |
| Клиент читает | сразу | **`Recv()` в цикле** | один раз | `Recv()` в цикле |
| Клиент пишет | — | — | `Send()` в цикле | `Send()` в горутине |
| Завершение | автомат. | **`io.EOF` на `Recv`** | `CloseAndRecv()` | `CloseSend()` + `io.EOF` |
| Контекст | `WithTimeout` | **`WithCancel` + Ctrl+C** | `WithTimeout` | `WithCancel` + Ctrl+C |

Server Streaming — первое место, где отмена через контекст становится
**обязательной**, а не «хорошей практикой». Без неё клиент может висеть
бесконечно.
