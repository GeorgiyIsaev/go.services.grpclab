# ClientUnary

Клиент **Unary RPC** — самый простой из четырёх паттернов gRPC.

Делает **один** запрос и получает **один** ответ. Никаких потоков, никаких
горутин, никакого `Recv`/`Send` в цикле. Просто «дай мне число» — и число
приходит.

Этот клиент — отправная точка. Если вы понимаете Unary, остальные три паттерна
воспринимаются как его естественные расширения: «а что если ответов будет
много», «а что если запросов будет много», «а что если и то, и другое».

---

## 🎯 Что делает клиент

1. Открывает gRPC-соединение с `ServerRandom` на `localhost:50051`.
2. Делает один вызов метода `GetRandom`.
3. Печатает полученное число в консоль.
4. Завершается.

Никаких циклов, повторных вызовов и ожиданий. Одна операция — один результат.

---

## 📚 Теория: Unary RPC

### Определение

**Unary RPC** — это паттерн, в котором клиент отправляет **одно** сообщение,
а сервер возвращает **одно** сообщение. Классический запрос-ответ, знакомый
по HTTP или обычному вызову функции.

### Как выглядит в `.proto`

```protobuf
rpc GetRandom(GetRandomRequest) returns (GetRandomResponse);
```

Ключевой признак: **`stream` отсутствует с обеих сторон**. Ни слева от
`returns` (клиент шлёт одно), ни справа (сервер отвечает одним).

### Как выглядит в Go

**Клиент:**
```go
resp, err := client.GetRandom(ctx, req)
```

**Сервер:**
```go
func (s *server) GetRandom(ctx context.Context, req *pb.GetRandomRequest) (*pb.GetRandomResponse, error)
```

Обе стороны работают с обычными аргументами и возвращаемыми значениями —
никаких стримов.



Клиент использует общий пакет `gen/randompb`, сгенерированный из
`proto/random.proto`. Метод `GetRandom` определён в том же `.proto`, что и
остальные три.

## 📝 Разбор кода

```go
package main

import (
	"context"
	"log"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/credentials/insecure"

	pb "go.services.grpclab/gen/randompb"
)

func main() {
	// 1. Соединение с сервером.
	conn, err := grpc.NewClient(
		"localhost:50051",
		grpc.WithTransportCredentials(insecure.NewCredentials()),
	)
	if err != nil {
		log.Fatalf("не удалось подключиться: %v", err)
	}
	defer conn.Close()

	client := pb.NewRandomClient(conn)

	// 2. Контекст с дедлайном.
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	// 3. Один запрос — один ответ.
	log.Println("отправляем запрос GetRandom...")

	resp, err := client.GetRandom(ctx, &pb.GetRandomRequest{})
	if err != nil {
		log.Fatalf("ошибка вызова: %v", err)
	}

	log.Printf("получено число: %d", resp.GetValue())
}
```

### Пошаговый разбор

**`grpc.NewClient(...)` — установка соединения.**

Создаёт клиентское соединение с сервером. В отличие от `grpc.Dial` (устаревшая
форма), `NewClient` подключается **лениво** — реальный TCP-коннект произойдёт
при первом вызове метода.

`insecure.NewCredentials()` используется, потому что у сервера нет TLS. В
продакшене здесь будет `credentials.NewTLS(...)`.

**`pb.NewRandomClient(conn)` — обёртка над соединением.**

Это сгенерированная функция. Она возвращает объект с методами, каждый из
которых соответствует `rpc` в `.proto`. Для нашего сервиса `Random` таких
методов четыре — по одному на паттерн.

**`context.WithTimeout(...)` — дедлайн на вызов.**

Каждый gRPC-вызов принимает `context.Context`. Через него передаются отмена
и дедлайн. `5*time.Second` — это не «сколько ждать ответ», а «сколько ждать
завершения всего вызова». Если сервер не ответит за 5 секунд, вызов
прервётся с ошибкой `DeadlineExceeded`.

`defer cancel()` обязателен — он останавливает внутренний таймер, иначе
произойдёт небольшая утечка ресурсов. Это ловит `go vet`.

**`client.GetRandom(ctx, &pb.GetRandomRequest{})` — сам вызов.**

Одна строка делает всё: сериализует запрос в бинарный формат, отправляет по
HTTP/2, ждёт ответ, десериализует его обратно в `GetRandomResponse`. Для
клиента это выглядит как вызов локальной функции.

Заметьте: `GetRandomRequest` пустой. В protobuf пустое сообщение — это
легально, оно сериализуется в ноль байт. Параметров у метода нет, поэтому
клиент шлёт «пустышку».

**`resp.GetValue()` — чтение результата.**

`GetValue()` — это **метод-геттер**, а не поле. `protoc-gen-go` генерирует
геттеры для каждого поля. Они безопасны к `nil`-получателю: если бы `resp`
был `nil`, `GetValue()` вернул бы `0`, а не панику.

## 🧪 Что попробовать

**1. Запустить несколько раз подряд.**

```powershell
go run ./cmd/ClientUnary
go run ./cmd/ClientUnary
go run ./cmd/ClientUnary
```

Каждый раз новое число. Убеждаемся, что сервер отвечает стабильно и
мгновенно.

**2. Запустить без сервера.**

Закройте сервер и запустите клиент. Через 5 секунд увидите:
```
ошибка вызова: rpc error: code = DeadlineExceeded desc = context deadline exceeded
```

Это работает дедлайн из `context.WithTimeout`. **Уберите его** — и клиент
будет ждать неопределённо долго (точнее, до таймаута TCP на уровне ОС, что
может занять минуты). Дедлайн — обязательная практика в реальном коде.

**3. Поставить смехотворно маленький дедлайн.**

```go
ctx, cancel := context.WithTimeout(context.Background(), 1*time.Nanosecond)
```

Сервер физически не успеет ответить. Та же ошибка `DeadlineExceeded`, но по
другой причине: раньше её вызывало отсутствие сервера, теперь — нереалистичный
дедлайн. Ощутите разницу.

**4. Проверить через `grpcurl`.**

Сервер включает reflection, поэтому можно дёрнуть метод без `.proto` файла:
```powershell
grpcurl -plaintext localhost:50051 random.Random/GetRandom
```

Ответ:
```json
{
  "value": 7
}
```

**5. Запустить несколько клиентов одновременно.**

Откройте 5 терминалов и запустите клиента в каждом. Сервер обработает все
параллельно — каждый в своей горутине — и каждый получит своё число. Никаких
конфликтов, никакой очереди.

## ⚠️ Типичные ошибки

**`cannot use resp.GetValue (value of type func() int32) as int32 value`**

Забыли скобки у геттера. `GetValue` — это метод, а не поле. Правильно:
`resp.GetValue()`.

**`rpc error: code = Unavailable desc = connection error`**

Сервер не запущен или слушает другой порт. Проверьте `ServerRandom` — он
должен быть поднят и напечатать `gRPC-сервер Random слушает :50051`.

**`context deadline exceeded`**

Сервер не ответил за отведённое время. Либо сервер лежит, либо дедлайн
слишком маленький. По умолчанию у нас 5 секунд — этого с запасом хватает для
локального вызова.

**`address already in use` на сервере**

Где-то остался висеть старый процесс на порту 50051. Закройте все окна с
`go run` через диспетчер задач, потом запустите сервер заново.

## 🧠 Ключевые выводы

1. **Unary — это один вызов = один результат.** Никаких потоков и циклов.
2. **Весь обмен умещается в одну строку:**
   `resp, err := client.GetRandom(ctx, req)`.
3. **Контекст обязателен и должен иметь дедлайн.** Без него клиент может
   висеть бесконечно.
4. **`defer cancel()` — обязателен.** Даже если вызов успешен, таймер
   контекста нужно остановить.
5. **Геттеры — методы.** `resp.GetValue()` со скобками, `resp.GetValue`
   без скобок — это функция, а не число.
6. **`grpc.NewClient` подключается лениво.** Ошибка соединения проявляется
   при первом вызове, а не при создании клиента.
7. **Unary — фундамент.** Все остальные паттерны — это тот же Unary, но с
   потоками в одну или обе стороны.
