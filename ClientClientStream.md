# ClientClientStream

Клиент **Client Streaming RPC** — третий из четырёх паттернов.

Клиент отправляет **поток** сообщений, а сервер, прочитав их все, отвечает
**одним** итоговым сообщением. Это зеркало Server Streaming: там читал
клиент, а писал сервер; здесь — наоборот.

Этот паттерн — рабочий инструмент для сценариев «данных много, а результат
один»: загрузка файла кусками, сбор телеметрии, батчевая обработка. Сервер
играет роль **аккумулятора и обработчика**, а клиент — роль **источника
потока**.

---

## 🎯 Что делает клиент

1. Открывает gRPC-соединение с `ServerRandom` на `localhost:50051`.
2. Открывает поток на отправку через `client.UploadNumbers(ctx)`.
3. Отправляет **10 случайных чисел** от 1 до 9 с паузой 500 мс между ними.
4. Вызывает `CloseAndRecv()` — сообщает серверу, что отправка завершена, и
   ждёт единственный ответ.
5. Печатает агрегат от сервера: количество, сумму, среднее, минимум, максимум.

Сервер накапливает статистику по мере поступления чисел и возвращает итог
только в конце — после того, как получит сигнал «клиент закончил».

## 📚 Теория: Client Streaming RPC

### Определение

**Client Streaming RPC** — паттерн, в котором клиент отправляет **поток**
сообщений, а сервер отвечает **одним** сообщением. Ответ приходит не на
каждое сообщение, а **один раз в конце**, после того как клиент явно
сообщит о завершении отправки.

Ключевая идея: клиент — источник множества однотипных данных, сервер —
аккумулятор и обработчик. По сети уходит N сообщений туда и 1 обратно.

### Как выглядит в `.proto`

```protobuf
rpc UploadNumbers(stream UploadNumbersRequest) returns (UploadNumbersResponse);
```

Ключевой признак: **`stream` стоит слева** от `returns`, перед типом запроса.
Это буквально читается как «клиент шлёт поток `UploadNumbersRequest`».

Справа `stream` нет — сервер отвечает одним сообщением.

### Как выглядит в Go

**Клиент:**
```go
stream, err := client.UploadNumbers(ctx)   // нет второго аргумента с req
for {
    stream.Send(&pb.UploadNumbersRequest{Value: v})
}
resp, err := stream.CloseAndRecv()         // закрываем и читаем один ответ
```

**Сервер:**
```go
func (s *server) UploadNumbers(stream pb.Random_UploadNumbersServer) error {
    for {
        req, err := stream.Recv()
        if errors.Is(err, io.EOF) {
            return stream.SendAndClose(resp)  // клиент закончил → отвечаем
        }
        // ...обработка req
    }
}
```

Два важных отличия от предыдущих паттернов:
- У клиента **нет второго аргумента с запросом** — запросов много, они уходят через `Send()`.
- У сервера **нет аргумента `req`** — запросы приходят через `Recv()`.

### Как сервер понимает, что пора отвечать

Это самый частый вопрос про Client Streaming. Ответ: **не по количеству
сообщений** — числа `10` нигде в контракте нет. Сервер узнаёт о конце потока
через специальный сигнал — **`io.EOF`**.

Проследим цепочку:

1. Клиент вызывает `stream.Send(...)` десять раз. Сервер в цикле `Recv()`
   получает десять сообщений.
2. Клиент вызывает `stream.CloseAndRecv()`. Это отправляет серверу
   служебный фрейм «я больше не буду писать».
3. Следующий `stream.Recv()` на сервере возвращает **не сообщение, а
   `io.EOF`**.
4. Сервер понимает: «клиент закончил». Формирует ответ и вызывает
   `stream.SendAndClose(resp)`.
5. `CloseAndRecv()` на клиенте получает это сообщение и возвращает его как
   результат.

Число `10` — это переменная в клиентском коде (`total := 10`). Оно **не
передаётся** серверу. Сервер не знает заранее, сколько сообщений будет — он
читает, пока не увидит `io.EOF`.

## 📝 Разбор кода

```go
package main

import (
	"context"
	"log"
	"math/rand"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/credentials/insecure"

	pb "go.services.grpclab/gen/randompb"
)

func main() {
	conn, err := grpc.NewClient(
		"localhost:50051",
		grpc.WithTransportCredentials(insecure.NewCredentials()),
	)
	if err != nil {
		log.Fatalf("не удалось подключиться: %v", err)
	}
	defer conn.Close()

	client := pb.NewRandomClient(conn)

	ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
	defer cancel()

	stream, err := client.UploadNumbers(ctx)
	if err != nil {
		log.Fatalf("не удалось открыть поток: %v", err)
	}

	total := 10
	log.Printf("начинаем отправку %d чисел...", total)
	for i := 1; i <= total; i++ {
		v := int32(rand.Intn(9) + 1)

		if err := stream.Send(&pb.UploadNumbersRequest{Value: v}); err != nil {
			log.Fatalf("ошибка отправки #%d: %v", i, err)
		}
		log.Printf("отправлено #%d: %d", i, v)

		time.Sleep(500 * time.Millisecond)
	}

	resp, err := stream.CloseAndRecv()
	if err != nil {
		log.Fatalf("ошибка получения итога: %v", err)
	}

	log.Println("--- итог от сервера ---")
	log.Printf("количество: %d", resp.GetCount())
	log.Printf("сумма:      %d", resp.GetSum())
	log.Printf("среднее:    %.2f", resp.GetAverage())
	log.Printf("минимум:    %d", resp.GetMin())
	log.Printf("максимум:   %d", resp.GetMax())
}
```

### Пошаговый разбор

**`context.WithTimeout(..., 30*time.Second)` — дедлайн на весь сеанс.**

В Server Streaming мы использовали `WithCancel` + Ctrl+C, потому что поток
мог быть бесконечным. Здесь поток **конечный** — мы знаем, что отправим
10 чисел. Поэтому логичнее поставить общий дедлайн на весь вызов: если
что-то затянется больше 30 секунд, что-то пошло не так.

`30 секунд` — это «сумма отправки (10 × 0.5 сек = 5 сек) + запас на
обработку и сетевую задержку». В реальном коде дедлайн подбирается под
сценарий.

**`client.UploadNumbers(ctx)` — открытие потока, без аргументов.**

Сравните с предыдущими паттернами:

```go
// Unary: возвращается сразу ответ
resp, err := client.GetRandom(ctx, req)

// Server Stream: возвращается стрим, есть аргумент req
stream, err := client.StreamRandom(ctx, req)

// Client Stream: возвращается стрим, НЕТ аргумента req
stream, err := client.UploadNumbers(ctx)
```

Отсутствие аргумента `req` — прямое следствие `.proto`:

```protobuf
rpc UploadNumbers(stream UploadNumbersRequest) returns (UploadNumbersResponse);
```

`stream` слева — значит, запросов много. Много запросов не передашь одним
аргументом, поэтому его нет. Все запросы уходят через `Send()`.

**`stream.Send(...)` в цикле — клиент как источник потока.**

`Send` кладёт сообщение в буфер, откуда gRPC его отправляет по сети. Метод
возвращает ошибку, только если что-то сломалось: соединение порвалось,
контекст отменён, сервер закрыл поток (`io.EOF`).

`Send` **не ждёт ответа**. Это принципиальное отличие от Unary: здесь нет
пары «отправил — получил». Отправка и приём разведены: `Send` идёт своим
чередом, ответ придёт только в самом конце через `CloseAndRecv`.

**`stream.CloseAndRecv()` — сигнал «я закончил» + чтение ответа.**

Это ключевой момент всего паттерна. `CloseAndRecv` делает **две вещи
одновременно**:

1. **Закрывает клиентскую сторону потока** — сообщает серверу: «я закончил,
   больше сообщений не будет». На сервере это проявится как `io.EOF` в
   `stream.Recv()`.
2. **Ждёт одно ответное сообщение** от сервера. Возвращает его как
   результат вызова.

Без `CloseAndRecv` сервер никогда не узнает, что клиент закончил, и будет
ждать вечно. Это **обязательный** финал для Client Streaming.

Важно: `CloseAndRecv` — не «закрыть соединение». Соединение остаётся
открытым, закрывается только **направление клиент → сервер**.

**`resp.GetCount()`, `GetSum()`, ... — геттеры со скобками.**

Все поля в `UploadNumbersResponse` читаются через методы. Геттеры безопасны
к `nil`-получателю, поэтому стиль единообразен с предыдущими клиентами.

**`resp.GetAverage()` возвращает `float64`.**

Сервер посчитал `float64(sum) / float64(count)` и упаковал в поле `double`.
Формат `%.2f` в `log.Printf` округляет до двух знаков.

## 🧪 Что попробовать

**1. Отправить ноль чисел.**

Поставьте `total := 0`. Цикл `Send` не выполнится, `CloseAndRecv` сразу
отправит `io.EOF` серверу. В серверном коде есть обработка `count == 0` —
вернётся пустой ответ. В клиенте увидите нули.

Это проверка крайнего случая: **протокол должен корректно работать и с
пустым потоком**. Многие баги в реальных системах вылезают именно на
«пустых» данных.

**2. Отправить 1000 чисел.**

Поставьте `total := 1000`, паузу уменьшите до 1 мс. Убедитесь, что сервер
считает всё корректно. Обратите внимание: по сети ушло 1000 сообщений,
а ответ пришёл **один**. Это то, ради чего Client Streaming и существует —
экономия на накладных расходах при передаче множества однотипных данных.

**3. Уронить сервер посреди отправки.**

Запустите клиент, через 2 секунды нажмите Ctrl+C в терминале сервера.
Следующий `stream.Send` вернёт ошибку вроде `Unavailable` — клиент упадёт
с `log.Fatalf`. Это **не** `io.EOF`, это настоящая ошибка: сервер не закрыл
поток корректно, он просто исчез.

**4. Поставить слишком короткий дедлайн.**

Поменяйте `30*time.Second` на `2*time.Second`, оставив паузу 500 мс × 10
чисел = 5 секунд. Клиент прервётся на середине отправки с ошибкой
`context deadline exceeded`. Так работает защита от «зависших» вызовов.

**5. Проверить через `grpcurl`.**

`grpcurl` умеет читать JSON-поток из stdin. Три числа:
```powershell
'{"value": 1}{"value": 5}{"value": 3}' | grpcurl -plaintext -d @ localhost:50051 random.Random/UploadNumbers
```

Ответ:
```json
{
  "count": 3,
  "sum": 9,
  "average": 3,
  "min": 1,
  "max": 5
}
```

Удобный способ быстро проверить серверную логику без написания кода.

**6. Два клиента одновременно.**

Запустите клиент в двух окнах. В логах сервера строки будут чередоваться,
но **каждый `[ClientStream] итог` относится к своему потоку**: числа не
смешались, `count` у каждого ровно 10. Переменные внутри метода `UploadNumbers`
локальны для вызова, поэтому гонок нет.

## ⚠️ Типичные ошибки

**`ошибка отправки #1: EOF`**

`Send` вернул `EOF` на первом же вызове — это значит, **сервер закрыл поток
сразу**. Самая частая причина в учебном проекте: на порту 50051 висит
**старый сервер**, который не знает метода `UploadNumbers`. Сервер отвечает
статусом `Unimplemented` и закрывает поток.

Решение: убедиться, что запущен **новый** `ServerRandom`, а не какой-то
старый процесс. Проверить через:
```powershell
grpcurl -plaintext localhost:50051 describe random.Random
```
Должны увидеть все четыре метода.

**`address already in use` на сервере**

На порту висит старый процесс. Закрыть все окна с `go run` через диспетчер
задач и запустить сервер заново.

**Забытый `CloseAndRecv`**

Если не вызвать `CloseAndRecv`, сервер никогда не увидит `io.EOF` и будет
ждать вечно. Клиент тоже будет висеть, пока не сработает дедлайн. В логах
сервера при этом не будет строки `итог: ...`.

**`context deadline exceeded`**

Клиент не успел завершить сеанс за отведённое время. Либо дедлайн слишком
маленький, либо сервер не отвечает. По умолчанию у нас 30 секунд — должно
хватать с запасом.

**Забыт `defer cancel()`**

`go vet` это поймает. Всегда `defer cancel()` сразу после
`context.WithTimeout`.

## 🧠 Ключевые выводы

1. **Поток идёт от клиента к серверу.** Клиент — источник данных, сервер —
   аккумулятор и обработчик.
2. **Один вызов клиента = много `Send` + один `CloseAndRecv`.**
3. **`CloseAndRecv()` — обязательный финал.** Без него сервер будет ждать
   вечно. Это единственный способ сообщить «я закончил».
4. **`io.EOF` на сервере — сигнал «клиент закончил».** Не путать с ошибкой.
5. **Сервер отвечает ровно один раз, в самом конце**, через `SendAndClose`.
6. **Симметрия с Server Streaming.** Там поток шёл в одну сторону, здесь —
   в другую. Код зеркальный: `Send` в цикле на клиенте ↔ `Recv` в цикле
   на сервере.
7. **`CloseSend()` и `CloseAndRecv()` — разные методы.**
    - `CloseSend` просто закрывает отправку, ответ не читает (используется
      в Bidi).
    - `CloseAndRecv` закрывает отправку **и** читает один ответ (используется
      в Client Streaming).
8. **Client Streaming выгоден при больших объёмах.** Один набор HTTP/2
   заголовков вместо N. При передаче тысяч однотипных сообщений экономия
   существенная.

## 🎯 Где это применяется в реальной жизни

Client Streaming — рабочий инструмент для сценариев «данных много, результат
один»:

- **Загрузка файла кусками.** Клиент режет файл на чанки и шлёт по одному.
  Сервер собирает, проверяет, сохраняет. В конце отвечает: «принято 10 МБ,
  хеш совпадает».
- **Сбор телеметрии с датчика.** Устройство раз в секунду шлёт показание.
  Сервер накапливает и в конце сессии отдаёт отчёт: min/max/avg за период.
- **Батчевая обработка.** Клиент шлёт 10 000 записей из CSV. Сервер
  валидирует, пишет в БД, возвращает «вставлено 9 998, две отбракованы».
- **Логи приложения.** Клиент шлёт лог-строки по мере поступления. Сервер
  копит, а в конце возвращает сводку (сколько error, warning, info).
- **ML-обучение.** Клиент шлёт батчи данных, сервер аккумулирует градиент
  и в конце возвращает обновлённую модель.

Общая формула: **клиент — источник множества однотипных событий, сервер —
аккумулятор и обработчик**.

### Где Client Streaming НЕ подходит

- **Нужен ответ на каждое сообщение.** Тогда это Bidi.
- **Сообщений мало (1–3).** Unary проще и дешевле.
- **Клиент хочет получать промежуточный фидбэк.** Client Streaming молчит
  до `CloseAndRecv`. Если нужен отклик в процессе — Bidi.

## 🔗 Сравнение с другими паттернами

| Что | Unary | Server Stream | **Client Stream** | Bidi |
|---|---|---|---|---|
| Клиент шлёт | 1 | 1 | **поток** | поток |
| Сервер шлёт | 1 | поток | **1** | поток |
| Клиент читает | сразу | `Recv()` в цикле | **один раз** | `Recv()` в цикле |
| Клиент пишет | — | — | **`Send()` в цикле** | `Send()` в горутине |
| Завершение | автомат. | `io.EOF` на `Recv` | **`CloseAndRecv()`** | `CloseSend()` + `io.EOF` |
| Серверный `io.EOF` | — | — | **сигнал «клиент закончил»** | сигнал «клиент закончил» |
| Где агрегация | — | клиент | **сервер** | обе стороны |
