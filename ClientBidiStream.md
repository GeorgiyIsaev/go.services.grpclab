# ClientBidiStream

Клиент **Bidirectional Streaming RPC** — четвёртый и последний паттерн.
Самый гибкий и самый сложный.

Обе стороны **одновременно** пишут и читают. Порядок сообщений в каждом
направлении сохраняется, но между направлениями нет никакой корреляции:
клиент может отправить десять сообщений, не получив ни одного ответа,
а сервер может ответить на первое только через секунду после десятого.
Это два независимых потока, живущих в рамках одного вызова.

Если Unary — это «спросил-ответил», Server Streaming — «подписался-слушаю»,
Client Streaming — «загрузил-получил итог», то Bidi — это **полноценный
диалог**: обе стороны говорят, когда хотят, и слушают, когда хотят.

---

## 🎯 Что делает клиент

1. Открывает gRPC-соединение с `ServerRandom` на `localhost:50051`.
2. Открывает двунаправленный поток через `client.CompareNumbers(ctx)`.
3. Запускает **отдельную горутину** для отправки: она шлёт 10 случайных
   чисел с паузой 500 мс, потом вызывает `CloseSend()`.
4. В **основной горутине** читает ответы сервера в цикле `Recv()`.
5. Сервер на каждое полученное число отвечает своим случайным числом и
   вердиктом «кто больше» (`client bigger`, `server bigger`, `equal`).
6. По Ctrl+C клиент корректно отменяет контекст — оба потока закрываются.

## 📚 Теория: Bidirectional Streaming RPC

### Определение

**Bidirectional Streaming RPC** — паттерн, в котором **обе стороны**
отправляют **потоки** сообщений. Клиент шлёт много, сервер шлёт много,
независимо друг от друга.

Это единственный паттерн, где и у клиента, и у сервера есть и `Send`, и
`Recv`. Все предыдущие три были частными случаями: где-то писал только
клиент, где-то только сервер, где-то оба писали по одному разу.

### Как выглядит в `.proto`

```protobuf
rpc CompareNumbers(stream CompareNumbersRequest) returns (stream CompareNumbersResponse);
```

Ключевой признак: **`stream` стоит с обеих сторон** от `returns`. Читается
буквально: «клиент шлёт поток `CompareNumbersRequest`, сервер отвечает
потоком `CompareNumbersResponse`».

### Как выглядит в Go

**Клиент:**
```go
stream, err := client.CompareNumbers(ctx)   // ни req, ни возврата

go func() {                                 // отправка в горутине
    for {
        stream.Send(...)
    }
    stream.CloseSend()                      // конец отправки
}()

for {                                       // чтение в основной
    resp, err := stream.Recv()
    if errors.Is(err, io.EOF) { break }
}
```

**Сервер:**
```go
func (s *server) CompareNumbers(stream pb.Random_CompareNumbersServer) error {
    for {
        req, err := stream.Recv()
        if errors.Is(err, io.EOF) { return nil }
        // ...обработка
        stream.Send(resp)
    }
}
```

Ключевые отличия от предыдущих паттернов:
- У клиента **нет ни аргумента `req`, ни возврата** — общаемся только через `Send`/`Recv`.
- У сервера **нет ни `req`, ни возврата** — то же самое.
- И клиент, и сервер **одновременно** держат открытыми оба направления.

### Почему нужны две горутины

`stream.Send()` и `stream.Recv()` — **блокирующие** операции. `Send`
блокируется, пока сообщение не уйдёт в буфер. `Recv` блокируется, пока не
придёт следующее сообщение.

Если делать и то, и другое в одной горутине, придётся строго чередовать:
отправил — прочитал — отправил — прочитал. Это уже не совсем Bidi: настоящий
двунаправленный поток позволяет писать и читать **независимо**. Клиент
может «выстрелить» десять сообщений подряд и только потом начать читать.

Поэтому отправку выносят в отдельную горутину, а чтение оставляют в
основной. Это стандартная практика для Bidi на клиенте. На сервере обычно
пишут один цикл `for { Recv }` и отвечают сразу — но при желании тоже можно
разнести на две горутины.

### `CloseSend` vs `CloseAndRecv`

Важное отличие от Client Streaming:

| | Client Streaming | Bidi |
|---|---|---|
| Как закончить отправку | `CloseAndRecv()` | `CloseSend()` |
| Что делает | Закрывает отправку **и читает один ответ** | Только закрывает отправку |
| Что с чтением | Одно сообщение, получено сразу | Много, читаются в цикле |
| Ответ сервера | Ровно один, обязателен | Ноль или много, по ситуации |

В Client Streaming сервер **обязан** прислать одно сообщение, поэтому клиент
может «закрыть и сразу прочитать». В Bidi сервер сам решает, сколько
ответов прислать и когда. Поэтому `CloseAndRecv` не подходит — он бы
заблокировался в ожидании ровно одного ответа, а их может быть много.

## 📝 Разбор кода

```go
package main

import (
	"context"
	"errors"
	"io"
	"log"
	"math/rand"
	"os"
	"os/signal"
	"sync"
	"syscall"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/credentials/insecure"

	pb "go.services.grpclab/gen/randompb"
)

func main() {
	conn, err := grpc.NewClient(
		"localhost:50051",
		grpc.WithTransportCredentials(insecure.NewCredentials()),
	)
	if err != nil {
		log.Fatalf("не удалось подключиться: %v", err)
	}
	defer conn.Close()

	client := pb.NewRandomClient(conn)

	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	sigCh := make(chan os.Signal, 1)
	signal.Notify(sigCh, os.Interrupt, syscall.SIGTERM)
	go func() {
		<-sigCh
		log.Println("получен сигнал, закрываем поток...")
		cancel()
	}()

	stream, err := client.CompareNumbers(ctx)
	if err != nil {
		log.Fatalf("не удалось открыть поток: %v", err)
	}

	log.Println("поток открыт, начинаем обмен...")

	var wg sync.WaitGroup
	wg.Add(1)

	go func() {
		defer wg.Done()

		total := 10
		for i := 1; i <= total; i++ {
			v := int32(rand.Intn(9) + 1)

			if err := stream.Send(&pb.CompareNumbersRequest{Value: v}); err != nil {
				log.Printf("ошибка отправки #%d: %v", i, err)
				return
			}
			log.Printf("отправлено #%d: %d", i, v)

			time.Sleep(500 * time.Millisecond)
		}

		if err := stream.CloseSend(); err != nil {
			log.Printf("ошибка CloseSend: %v", err)
		}
		log.Println("отправка завершена, ждём последние ответы...")
	}()

	for {
		resp, err := stream.Recv()

		if errors.Is(err, io.EOF) {
			log.Println("сервер закрыл поток")
			break
		}
		if err != nil {
			if ctx.Err() != nil {
				log.Println("поток закрыт клиентом")
				break
			}
			log.Printf("ошибка приёма: %v", err)
			break
		}

		log.Printf("ответ: client=%d server=%d → %s",
			resp.GetClientValue(),
			resp.GetServerValue(),
			resp.GetResult(),
		)
	}

	wg.Wait()
	log.Println("завершено")
}
```

### Пошаговый разбор

**`context.WithCancel` + Ctrl+C — как в Server Streaming.**

Поток может быть сколь угодно долгим, поэтому вместо дедлайна используем
управляемую отмену. Ctrl+C → `cancel()` → оба направления закрываются →
сервер узнаёт об этом через `stream.Context().Done()`.

**`client.CompareNumbers(ctx)` — открытие двунаправленного потока.**

Ни аргумента, ни возврата. Это прямое следствие `.proto`:

```protobuf
rpc CompareNumbers(stream CompareNumbersRequest) returns (stream CompareNumbersResponse);
```

`stream` с обеих сторон — значит, ни запроса как аргумента, ни ответа как
возврата. Всё общение через `Send` и `Recv` на объекте `stream`.

**`sync.WaitGroup` — чтобы `main` не завершился раньше горутины.**

Отправка живёт в отдельной горутине. Без `wg.Wait()` основная горутина
может выйти из цикла `Recv`, и `main` завершится, **не дождавшись**
отправителя. Это плохо: отправитель может писать в уже закрытый поток,
получать ошибки, писать в лог — в общем, вести себя неаккуратно.

`wg.Add(1)` перед запуском горутины, `defer wg.Done()` внутри неё,
`wg.Wait()` после цикла `Recv` — стандартный паттерн синхронизации.

**Горутина отправителя — `Send` в цикле с паузой.**

`stream.Send(...)` блокируется, пока сообщение не уйдёт в буфер. Пауза
500 мс делает поведение наглядным: сервер успевает отвечать на каждое
сообщение, и в логах видно чередование.

**`stream.CloseSend()` — конец отправки.**

Сообщает серверу: «я больше не буду писать». На сервере это проявится как
`io.EOF` на следующем `Recv()`. Обратите внимание: **чтение при этом
продолжается**. `CloseSend` закрывает только направление клиент → сервер.

**Основная горутина — `Recv()` в цикле.**

Как и в Server Streaming, читаем в цикле, пока не получим `io.EOF` (сервер
закрыл свою сторону) или ошибку. Проверка `ctx.Err() != nil` отличает
«сами отменили» от «что-то сломалось».

**`io.EOF` — сервер закончил отправку.**

В нашем серверном коде это происходит, когда сервер получил `io.EOF` от
клиента (после `CloseSend`) и вернул `nil` из метода. Тогда gRPC закрывает
поток с обеих сторон, и клиент на `Recv()` получает `io.EOF`.

**`wg.Wait()` после цикла.**

Дожидаемся горутины-отправителя и только потом завершаем программу. К
этому моменту `CloseSend` уже вызван, и всё чисто.

## 🧪 Что попробовать

**1. Убрать паузу.**

Удалите `time.Sleep(500 * time.Millisecond)` или поставьте `0`. Клиент
«выстрелит» все 10 сообщений почти мгновенно. Сервер всё равно ответит на
каждое — просто ответы придут с небольшой задержкой, потому что сеть и
горутины не мгновенны.

Это наглядное доказательство, что **Send и Recv действительно независимы**.
В Unary такого не бывает: там пока не отправил — нечего читать.

**2. Сделать отправку быстрее обработки.**

Увеличьте `total` до 1000 и уберите паузу. Вы увидите, что клиент отправит
всё раньше, чем получит последние ответы. Поток работает как конвейер:
сообщения «в пути» и «в обработке» накапливаются, но gRPC справляется с
этим через flow control HTTP/2.

Если поставить `total = 1_000_000`, вы увидите, что отправитель начнёт
подтормаживать: буфер заполнится, `Send` будет блокироваться до тех пор,
пока сервер не вычитает часть сообщений.

**3. Уронить сервер посреди обмена.**

Запустите клиент, через 2 секунды нажмите Ctrl+C в терминале сервера.
Клиент на `Recv()` получит ошибку `Unavailable`, выйдет из цикла, а
горутина-отправитель либо тоже упадёт на `Send`, либо завершится по
`CloseSend`. Программа корректно завершится.

Обратите внимание: **без `wg.Wait()` клиент мог бы завершиться до того,
как горутина-отправитель «проглотит» ошибку**. WaitGroup гарантирует, что
все ошибки будут залогированы до выхода.

**4. Нажать Ctrl+C в клиенте.**

До того как он сам закончит. Увидите:
```
получен сигнал, закрываем поток...
поток закрыт клиентом
```
А на сервере:
```
[Bidi] ошибка приёма: rpc error: code = Canceled ...
```
Или `клиент закрыл поток` — в зависимости от того, успел ли сервер получить
`io.EOF` или уже сработала отмена. Это показывает, как отмена контекста
распространяется в обе стороны.

**5. Два клиента одновременно.**

Запустите клиент в двух окнах. Каждый получит **свой независимый поток**:
своё расписание отправки, свои ответы. В логах сервера строки будут
чередоваться, но каждый набор «client=X server=Y» относится к своему
клиенту. Переменные внутри метода `CompareNumbers` локальны для вызова.

**6. Проверить через `grpcurl`.**

`grpcurl` читает JSON-поток из stdin и печатает ответы в реальном времени:
```powershell
'{"value": 1}{"value": 5}{"value": 3}' | grpcurl -plaintext -d @ localhost:50051 random.Random/CompareNumbers
```

Ответ:
```json
{"clientValue": 1, "serverValue": 7, "result": "server bigger"}
{"clientValue": 5, "serverValue": 2, "result": "client bigger"}
{"clientValue": 3, "serverValue": 3, "result": "equal"}
```

## ⚠️ Типичные ошибки

**Программа завершается раньше, чем отправитель дописал лог**

Забыт `wg.Wait()` после цикла `Recv`. `main` завершается, все горутины
убиваются вместе с процессом. В логах не видно последних строк от
отправителя. `WaitGroup` — обязателен.

**`Send` возвращает `EOF` на первом вызове**

Сервер закрыл поток сразу — скорее всего, на порту висит **старый сервер**,
у которого нет метода `CompareNumbers`. Проверьте через:
```powershell
grpcurl -plaintext localhost:50051 describe random.Random
```
Должны увидеть все четыре метода.

**Программа «зависает» после `CloseSend`**

Клиент закрыл отправку, но продолжает ждать `Recv`, а сервер не завершает
метод. В нашем серверном коде `CompareNumbers` выходит из цикла по `io.EOF`
и возвращает `nil` — тогда клиент получит `io.EOF` на `Recv`. Если бы
сервер не обрабатывал `io.EOF`, клиент висел бы бесконечно.

**Ответы приходят в неправильном порядке**

Это не ошибка. В Bidi нет гарантии соответствия «запрос N → ответ N».
Сервер отвечает по мере обработки, а два потока независимы. Если вам
нужна строгая корреляция — добавляйте ID в сообщения.

**Забыт `defer wg.Done()`**

Горутина-отправитель завершается, но `wg.Wait()` навсегда остаётся
заблокированным. Программа висит до Ctrl+C. Классический паттерн — писать
`defer wg.Done()` **сразу** после входа в горутину.

**Ошибка `SendMsg called after CloseSend`**

Попытка отправить сообщение после `CloseSend`. В нашем коде это невозможно,
потому что `CloseSend` — последняя операция в цикле отправки. Но если
случайно добавить `Send` после него — получите эту ошибку.

## 🧠 Ключевые выводы

1. **Обе стороны пишут и читают одновременно.** Это единственный паттерн,
   где и у клиента, и у сервера есть и `Send`, и `Recv`.
2. **Две горутины на клиенте — типичная реализация.** Одна шлёт, другая
   читает. Без этого приходится строго чередовать, что уже не совсем Bidi.
3. **`CloseSend()` вместо `CloseAndRecv()`.** Закрывает только отправку,
   оставляя чтение открытым.
4. **`sync.WaitGroup` — обязателен.** Иначе `main` завершится раньше
   горутины-отправителя, и часть логов/ошибок потеряется.
5. **Порядок обмена не гарантирован.** Нет корреляции «запрос N → ответ N».
   Если нужна — добавляйте ID.
6. **`io.EOF` на `Recv` — сервер закончил.** Клиент не должен падать, это
   штатное завершение потока.
7. **Bidi — самый гибкий паттерн.** В нём нет «правильного» порядка: обе
   стороны сами решают, когда что отправлять. Именно поэтому он и самый
   сложный.

## 🎯 Где это применяется в реальной жизни

Bidi Streaming — инструмент для **интерактивных сценариев**, где обе стороны
должны реагировать на события друг друга:

- **Чат.** Обе стороны пишут сообщения, когда хотят. Сервер пересылает
  участникам, следит за порядком, добавляет системные уведомления.
- **Игровые сессии.** Клиент шлёт команды игрока, сервер — состояние мира.
  Обе стороны работают в реальном времени.
- **Совместное редактирование.** Клиенты шлют изменения, сервер
  синхронизирует их между всеми участниками.
- **Телеметрия с управлением.** Клиент шлёт данные с датчика, сервер
  отвечает командами («повысь частоту», «перезагрузи сенсор»).
- **Голосовые/видео ассистенты.** Клиент шлёт фрагменты аудио, сервер
  возвращает транскрипцию и ответы по мере обработки.
- **Интерактивные оболочки** (gRPC shell). Клиент шлёт команды, сервер —
  поток вывода.

Общая формула: **две стороны ведут диалог в реальном времени, каждая может
инициировать сообщение**.

### Где Bidi НЕ подходит

- **Строгая схема «запрос-ответ».** Unary проще и понятнее.
- **Один запрос — много ответов от сервера.** Server Streaming достаточно.
- **Много запросов — один итог.** Client Streaming экономнее.
- **Нужна надёжная доставка с гарантией порядка.** gRPC гарантирует
  порядок внутри потока, но не даёт «доставлено и обработано». Для этого
  нужны ACK-механизмы поверх протокола.

## 🔗 Сравнение с другими паттернами

| Что | Unary | Server Stream | Client Stream | **Bidi** |
|---|---|---|---|---|
| Клиент шлёт | 1 | 1 | поток | **поток** |
| Сервер шлёт | 1 | поток | 1 | **поток** |
| Клиент читает | сразу | `Recv()` в цикле | один раз | **`Recv()` в цикле** |
| Клиент пишет | — | — | `Send()` в цикле | **`Send()` в горутине** |
| Завершение | автомат. | `io.EOF` на `Recv` | `CloseAndRecv()` | **`CloseSend()` + `io.EOF`** |
| Горутин на клиенте | 1 | 1 | 1 | **2** |
| Порядок обмена | строгий | только к клиенту | только от клиента | **независимый** |
| `WaitGroup` | нет | нет | нет | **обязателен** |

Bidi — единственный паттерн, где клиенту нужны **две горутины** и
**синхронизация**. Это плата за гибкость.
