ClientClientStream

В Client Streaming — клиент шлёт поток сообщений, а сервер, прочитав их все, отвечает одним итоговым сообщением.

Для тестов:

1. Измените количество чисел. Поставьте total := 100. Отправка быстрее (уменьшите паузу до 10 мс), сумма вырастет. Убедитесь, что сервер считает всё корректно.

2. Отправьте ноль чисел. Поставьте total := 0. Цикл не выполнится, CloseAndRecv отправит io.EOF серверу сразу. В серверном коде есть обработка count == 0 — вернёт пустой ответ. В клиенте увидите нули. Это проверка крайнего случая: протокол должен корректно работать и с пустым потоком.

3. Уроните сервер посреди отправки. Запустите клиент, а через 2 секунды нажмите Ctrl+C в терминале сервера. Следующий stream.Send вернёт ошибку вроде Unavailable — клиент упадёт с log.Fatalf. Обратите внимание: это не нормальное завершение (в отличие от io.EOF). Так и должно быть.

4. Уменьшите дедлайн контекста до 2 секунд (при паузе 500 мс × 10 чисел = 5 секунд). Клиент прервётся на середине отправки с ошибкой context deadline exceeded. Это показывает, зачем нужны дедлайны: без них клиент мог бы висеть вечно.

5. Проверьте через grpcurl. Хитрость: grpcurl умеет читать JSON-массив из stdin для клиентского потока. Пример с тремя числами:
```
{"value": 1}{"value": 5}{"value": 3}' | grpcurl -plaintext -d @ localhost:50051 random.Random/UploadNumbers
```


ИТОГ:
Один вызов клиента — много Send. Клиент — источник потока.

CloseAndRecv() — обязательный финал. Без него сервер будет ждать вечно. Это единственный способ сообщить «я закончил».

У клиента нет Recv() вообще. В клиентском стриминге клиент только пишет; единственное чтение — через CloseAndRecv, и оно возвращает ровно одно сообщение.

Симметрия с сервером. На сервере — Recv() в цикле до io.EOF, потом SendAndClose(resp). На клиенте — Send() в цикле, потом CloseAndRecv(). Это зеркала друг друга.

stream.CloseAndRecv() и stream.CloseSend() — разные вещи. CloseSend() просто закрывает отправку, но не читает ответ. Для клиентского стриминга используйте CloseAndRecv(), потому что сервер обязан прислать одно сообщение.


EOF при Send

В gRPC-Go stream.Send() возвращает io.EOF, когда сервер уже закрыл поток со своей стороны. Это не «соединение пропало» (тогда была бы ошибка Unavailable), а «сервер корректно завершил вызов, но ты пытаешься писать дальше».

Самая частая причина в учебном проекте: на порту 50051 работает старый сервер, который не знает метода UploadNumbers.

По сети ушло 10 сообщений туда, 1 обратно. Если бы это был Unary, клиенту пришлось бы либо отправлять все 10 чисел в одном огромном сообщении, либо делать 10 отдельных вызовов. Client Streaming даёт третий, более элегантный вариант: один вызов, много отправок, один ответ.
